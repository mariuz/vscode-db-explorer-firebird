# Backup/Restore: Expose gbak Options

**Inspired by**: [vscode-pgsql](https://github.com/microsoft/vscode-pgsql)'s Database Backup (Preview, 1.27.0) — "Choose Backup... from a server or database in Object Explorer to create a `pg_dump` backup. Configure the output format, schema/data scope, object filters, compression, parallel jobs, and advanced options, then monitor or cancel the backup from VS Code." — and its Database Restore (Preview, same release) — "Choose Restore... to recover from backup files, select the target database and restore mode (full/schema-only/data-only), preview the command, and monitor progress."

## Current state in Firebird Studio

**All four phases are done.** `NodeDatabase.backupDatabase()`/`.restoreDatabase()` (`src/nodes/node-database.ts`) run a real `gbak` subprocess with real progress reporting — a `showSaveDialog`/`showOpenDialog` for the file, a cancellable progress notification (phase 3, replacing the original status-bar spinner), and (since `docs/roadmap/connection-management-enhancements.md`'s phase 4) a Background Tasks entry.

- **Phase 1 — backup options — done.** `backupDatabase()` now shows a multi-select QuickPick (`BACKUP_OPTION_ITEMS`) before the file picker, offering the four flags below; leaving everything unchecked (or pressing Enter immediately) produces the exact same `args` array as before this phase — Escape/dismissed cancels the whole backup, matching the file picker's own existing cancel behavior. New `src/shared/gbak-options.ts`'s pure `buildBackupFlags(choices)` turns the picked checkboxes into the actual `-G`/`-ZIP`/`-M`/`-NT` flags, kept separate from the QuickPick/child-process code specifically so it's unit-testable without a real file dialog or subprocess. **All four flags verified directly against a real `gbak` (Firebird 6.0) run against the seeded test database** — `-G` (no size difference, as expected — garbage collection doesn't change backup content), `-M` (87552 vs 101376 bytes, correctly schema-only), `-ZIP` (11776 bytes, real compression), `-NT` (100352 bytes, smaller than the transportable default), and all four combined together (9728 bytes, exit code 0) — not just that the flags exist in `gbak -z`'s help text, but that Firebird's real `gbak` actually accepts and honors each one.
- **A genuine, separate pre-existing gap found and fixed while verifying phase 1 live**: `gbak` turned out to not be on `PATH` in this session's own sandbox at all (confirmed via `which gbak`) — only reachable at `/opt/firebird/bin/gbak` — yet `cp.execFile("gbak", args)` called a bare, unconfigurable binary name, unlike `isql`'s own `firebird.isqlPath` setting/`resolveIsqlExecutable()`. Fixed with a new `firebird.gbakPath` setting and `resolveGbakExecutable()`/`gbakCandidates()` (`gbak-options.ts`), mirroring `resolveIsqlExecutable()`/`resolveDockerExecutable()` exactly — this codebase already keeps these three small and independent rather than sharing one abstraction between them, so a third near-identical copy was written the same way rather than introducing a new shared helper the codebase hasn't asked for. **Superseded in part:** the three *resolvers* are still independent, but the spawn-based probe each one takes as an argument was later consolidated into `src/shared/executable-probe.ts` — the codebase did eventually ask for it, by hiding a bug in one of the copies (`checkIsqlExecutable()` reported a working isql as missing for as long as it existed; see docs/roadmap/isql-terminal-shell-integration.md). **One real wrinkle**: unlike isql's own `-z` (exits cleanly), a real `gbak -z` always exits non-zero — confirmed live, it still prints its version banner to stdout ("gbak:gbak version...") *then* errors with "requires both input and output filenames" since `-z` alone isn't a complete backup/restore command — so `extension.ts`'s new `checkGbakExecutable()` checks stdout for the version banner instead of the exit code, unlike `checkIsqlExecutable()`'s exit-code check. Both `backupDatabase()`/`restoreDatabase()` now take the resolved executable path as a parameter (defaulting to `"gbak"` for any caller that doesn't resolve one first) rather than hardcoding it. Verified against the real sandbox's actual broken state: unresolvable with no setting (matches reality), resolves correctly once `firebird.gbakPath` points at the real binary, and correctly refused for a bogus path.
- **Phase 2 — restore options — done.** `restoreDatabase()` (`src/nodes/node-database.ts`) now shows a multi-select QuickPick (`RESTORE_OPTION_ITEMS`) after the two file pickers, offering replace-an-existing-database, metadata only, one table at a time, skip validity conditions, don't recreate shadows, and override page size; a second QuickPick asks for the page size *only* when that box is ticked, so the common restore is still one extra dialog rather than two. Leaving everything unchecked produces `["-C", "-user", u, "-password", p, backup, target]` — byte-for-byte what this command sent before this phase, apart from `-c` now being spelled `-C`.
  - New pure `buildRestoreFlags()`/`buildRestoreArgs()`/`renderGbakCommand()` in `gbak-options.ts`, alongside phase 1's `buildBackupFlags()`. `buildRestoreArgs()` assembles the *whole* argument list rather than just the modifier flags, specifically so the command preview and the command actually executed are produced by the same function — a preview that can drift from what runs is worse than no preview at all.
  - **Every flag verified against a real `gbak` (Firebird 6.0) run against a real backup**, not from its help text alone: `-C` into a fresh path restores all 5 seeded `PRODUCTS` rows; `-C` onto an existing database fails with gbak's own "already exists. To replace it, use the -REP switch" (which is exactly what the "Replace an existing database" checkbox is for); `-REP` onto that same existing database succeeds with all 5 rows; `-M` produces a database whose `PRODUCTS` has 0 rows; and `-O -N -K -P 16384` combined exits 0 with `gstat -h` confirming a real 16384 page size. The "Firebird's default" label on the 8192 page-size entry was likewise confirmed against a freshly created FB6 database rather than assumed.
- **Phase 2 — command preview — done.** A modal `showWarningMessage` before the restore shows `renderGbakCommand()`'s rendering of the exact args, with the password replaced by `********` (the preview exists to be read by a human, so putting their password in it would be a poor trade). The warning text itself differs for a replace ("Its current contents will be lost.") versus a create. The same rendered line is also written to the output channel when the run starts, so the log records what was actually run.
- **Phase 3 — cancel — done, for both backup and restore.** The old status-bar spinner is replaced by `window.withProgress({location: Notification, cancellable: true})`, whose Cancel button calls `child.kill()` on the real `gbak` child process — cancelling actually stops the work rather than hiding its indicator. A cancelled run is recorded as failed ("Cancelled") in the Background Tasks view and says plainly that the output file may be incomplete. The Background Tasks entry is unchanged otherwise.
- **Phase 4 — parallel workers and multi-file backup — done.** Both are offered from the same options QuickPick each command already shows, each prompting further only when actually picked.
  - **Parallel workers (`-PAR n`), for backup *and* restore.** Only offered when the server can honor it: `getMaxParallelWorkersQuery()` reads `MaxParallelWorkers` from the `RDB$CONFIG` virtual table first, and the picker offers 2..max. This exists because of a live finding — `gbak -PAR 4` against this server (default `MaxParallelWorkers` = 1) prints `WARNING:Wrong parallel workers value 4, valid range are from 1 to 1` and then silently runs single-threaded, so an unconstrained picker would have quietly done nothing. When the cap is 1 the option says so instead of offering a useless prompt. Any failure reading the config (older server, no `RDB$CONFIG`) resolves to 1 rather than blocking the backup.
  - **Multi-file backup.** `buildMultiFileTargets()` emits gbak's own `file1 <size> file2 <size> … fileN` form, where every volume but the last carries a size. The user picks *one* path and a volume count/size; the rest are derived (`backup.fbk` → `backup.fbk`, `backup.2.fbk`, `backup.3.fbk`), keeping the extension so each part stays recognizable. A count of 1 collapses to exactly the pre-phase-4 single-file argument.
  - **Restore is now multi-file aware, which is what makes the above usable.** The file picker gained `canSelectMany`, and volumes are sorted *naturally* (so `backup.10.fbk` sorts after `backup.2.fbk`, not before). This matters more than it looks: confirmed live that handing gbak only the first volume of a multi-file backup makes it consume the *target* path as the next backup volume and fail with `cannot open backup file <target>` — an error that reads like a permissions problem rather than a missing file.
  - **The generated argument lists were run end-to-end against a real gbak**, not just unit-asserted: a 3-volume backup built by `buildMultiFileTargets()` produced two 40960-byte volumes plus a 5932-byte remainder, and the `buildRestoreArgs()` output listing all three restored a database with all 5 seeded `PRODUCTS` rows, both at exit 0.
- All four phases are now done.

## Proposed feature

`gbak` itself already supports the switches that would matter here — this is exposing existing `gbak` capability through UI, not building new backup logic. Verified directly against a real `gbak -z`'s own help output (Firebird 6.0) rather than trusted from memory — several of the flag letters originally guessed here turned out wrong (`-fa` is actually "blocking factor", not metadata-only; `-k` is "no shadows", not "no validity checks"):

- **Backup options** (`gbak -b` flags): `-G` (inhibit garbage collection, faster backup), `-NT` (non-transportable format — Firebird's own default *is* transportable, `-NT` opts out for a smaller/faster same-platform-only backup), `-M` (metadata only, no data), `-ZIP` (zip-compressed backup file), `-SE` (use the Services API instead of a local file-path connection, needed for a remote server without local `gbak` access to the file path). `-PAR n` (parallel workers, Firebird 4+) for large databases.
- **Restore options** (`gbak -c`/`-r`/`-rep` flags): `-P <size>` (override page size), `-O` (restore one table at a time, useful for diagnosing a restore failure), `-N` (skip restoring validity/`NOT NULL`/`CHECK` conditions), `-K` (restore without creating shadow files). Note `-REP`/`-R(ECREATE) OVERWRITE` are *top-level* restore-mode switches (used instead of `-C`, not alongside it) for replacing an already-existing database, not modifier flags — today's `restoreDatabase()` always uses `-C`, which fails outright if the target file already exists; offering "replace an existing database" needs switching the top-level flag, not adding one.
- A QuickPick-based "Backup options" step (matching this codebase's existing wizard patterns, e.g. `connection-wizard.ts`) before the file picker, defaulting to today's exact behavior (no flags — Firebird's own defaults) so nothing changes for anyone who doesn't open it.
- **A command preview before running** (pgsql 1.27.0 does this for restore specifically): show the assembled `gbak` command line — executable, flags, source, target — as a confirmation step, so a destructive restore isn't a blind "trust the checkboxes I ticked" action. This is nearly free once the args array is built, and matters most for restore, where the target file can be an existing database. The same rendered string is worth logging to the output channel either way, which `logger.info` already does partially ("Starting restore from X to Y") without the actual flags.
- **Restore mode as a first-class choice, not just flags.** pgsql offers full/schema-only/data-only; Firebird's `gbak` has no data-only restore (a restore always rebuilds metadata first), so the honest mapping is a two-item choice — full restore, or metadata-only (`-M`, the same switch the backup side already exposes, valid on restore too) — rather than mirroring pgsql's three modes for the sake of parity.
- **Cancel support**: `gbak` is a real child process (`cp.execFile`) already — a `Cancel` button on the status bar item or the Background Tasks entry could call `child.kill()`, not currently offered at all.
