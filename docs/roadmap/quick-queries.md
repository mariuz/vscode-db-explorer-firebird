# Quick Queries (keyboard-bound saved SQL)

**Inspired by**: [vscode-mssql](https://github.com/microsoft/vscode-mssql) (1.44.0) — "Introduced Shortcuts Configuration (Preview), allowing you to create and manage keyboard shortcuts for Quick Queries, the Query Editor, and the Results Grid" — and (1.44.1) — "Added support for selected text in Quick Query shortcuts". mssql's Quick Queries let you save frequently used SQL snippets, bind each to a keyboard shortcut, and choose whether the shortcut executes the query immediately or opens it in the editor for review.

## Current state in Firebird Studio

**Phases 1, 2, and 3 are done.** Phase 4 (a management webview) remains deliberately unbuilt — see below.

- **Phase 1 — setting + numbered commands — done.** New `src/shared/quick-queries.ts` (pure, no `vscode` import, unit-tested) holds the whole decision-making half: `parseQuickQueries()` normalizes the raw `firebird.quickQueries` setting, `resolveQuickQuery()` looks up a 1-based slot, `findBookmarkForSlot()` handles the bookmark fallback, and `applySelectedText()` does the placeholder substitution. `package.json` contributes `firebird.quickQuery.1` … `.9` (`QUICK_QUERY_SLOT_COUNT`) with **no default keybindings**, plus the `firebird.quickQueries` array setting with a JSON schema (`required: ["sql"]`, `action` enum) so VS Code's settings editor validates entries as they're typed. `extension.ts` registers all nine in one numeric loop dispatching to a shared `runQuickQuery(slot)`, which executes through **`runSqlBatch()`** — the same shared runner behind `firebird.runQuery`/`firebird.runCurrentStatement` — so a Quick Query gets multi-statement splitting, the DDL-success notification plus Object Explorer refresh, query-history logging, and the `{notify, message, options}` error handling for free rather than reimplementing any of it. `action: "open"` routes to the pre-existing `Driver.createSQLTextDocument()` instead, the same call `firebird.bookmarks.open` already uses.
  - **One design decision worth recording, because it's the non-obvious part**: an unusable entry parses to `null` *in place* rather than being filtered out. Slot numbers are positions users have bound keys to, so dropping a malformed entry would shift every later query up one slot and silently repoint a working keybinding at the wrong SQL — a data-loss-shaped bug rather than a cosmetic one. Covered by its own test.
- **Phase 2 — `${selectedText}` — done.** `applySelectedText()` substitutes the active editor's selection (trimmed), with two deliberate behaviors: a query using the placeholder with **nothing selected is refused** with an explanation rather than substituted with an empty string (which would produce `SELECT COUNT(*) FROM ` and a confusing server-side parse error), and substitution is `split`/`join` rather than `String.replace()`, because the replacement is arbitrary user-selected text and `replace()` expands `$&`/`` $` ``/`$1` inside it — a real hazard here, since Firebird's own system tables are named `RDB$RELATIONS` and friends. Both are tested. The selection is read from whatever editor is active, not only SQL documents, since highlighting a table name in a log or migration script is just as valid a source.
- **Phase 3 — bookmark slots — done.** `Bookmark` gained an optional `slot`, `BookmarkProvider.assignSlot()` binds/clears it, and **Assign to Quick Query Slot** (`firebird.bookmarks.assignSlot`, in the Bookmarks view's context menu) shows a QuickPick of all nine slots — each labelled with its current occupant, if any, since picking an occupied slot unbinds them. `assignSlot()` clears the slot from any other bookmark holding it, so a slot never has two claimants and resolution can't become insertion-order-dependent. A `firebird.quickQueries` setting entry wins over a bookmark for the same slot, as proposed below. The bookmark's tree description shows `Quick Query N` so a binding is visible without opening the menu.

### Testing

`src/test/quick-queries.test.ts` (17 tests) covers all four pure functions: `parseQuickQueries()` (non-array input, the minimal `{sql}` entry, first-line/40-char name derivation without truncating the SQL itself, explicit vs unrecognized `action`, and the null-placeholder-preserves-positions case with six different kinds of malformed entry); `resolveQuickQuery()` (1-based indexing, an unusable slot resolving to `undefined` rather than the next usable one, and out-of-range/zero/negative/non-integer/empty-list guards, plus entries past slot 9 parsing but staying unreachable); `findBookmarkForSlot()` (bound/unbound lookups, `0`/`NaN` guards, and first-wins for a duplicated slot); and `applySelectedText()` (no-placeholder passthrough, trimmed substitution, *all* occurrences replaced, `$`-bearing selections inserted literally, and refusal for undefined/empty/whitespace-only selections).

`src/test/suite/extension.test.ts`'s roadmap-command map gained a `quick-queries.md` entry checking `firebird.quickQuery.1`, `firebird.quickQuery.9`, and `firebird.bookmarks.assignSlot` — first and last slot deliberately, so an off-by-one in the registration loop or in `QUICK_QUERY_SLOT_COUNT` fails the suite rather than passing silently.

What's **not** covered by an automated test, consistent with this repo's established boundary: `runQuickQuery()`'s own command body and the `assignSlot` QuickPick are `extension.ts#activate()` orchestration (dialogs, editor selection, settings navigation), which isn't independently unit- or suite-testable here — the same boundary every other `commands.registerCommand()` callback in that file already sits behind. ### Original state (before this item)

Two of the three ingredients already existed separately, and neither one was connected to a keybinding.

- **`firebird.shortcuts` already exists but is a different feature with a confusingly similar name.** `DEFAULT_SHORTCUTS` (`src/config/config.ts`) mirrors `mssql.shortcuts` and covers six actions *inside the Query Results webview* only (`event.toggleEditing`, `event.addRow`, `event.applyChanges`, `event.toggleFreezeColumn`, `event.copyAsInsert`, `event.copyAsInClause`), handled by the webview's own keydown listener because a `contributes.keybindings` entry can't reach into webview content. Nothing here binds a *saved SQL query* to a key — that's mssql's separate "Quick Queries" tab, which Firebird Studio has no equivalent of.
- **Bookmarks are the closest thing to a saved-query store, and they can't be run.** `BookmarkProvider` (`src/bookmarks/bookmark-provider.ts`) persists named SQL in `context.globalState` with a tree view, but its five commands are `firebird.bookmarks.add`/`.open`/`.delete`/`.rename`/`.refresh` — `.open` only drops the text into a new editor, and the only bookmark keybinding is `ctrl+alt+b` for `.add`. There is no "run this bookmark against the active connection" command at all.
- **Snippets (`contributes.snippets`) are editor text templates**, expanded by prefix while typing — not connection-aware and not executable.
- **The constraint that shapes the design**: VS Code keybindings are declared statically in `package.json`, and users can't create new commands. So "bind an arbitrary saved query to a key" can only be done the way mssql does it — ship a fixed set of generic, numbered commands that users bind themselves in VS Code's own Keyboard Shortcuts editor, each dispatching to the *n*th configured query.

## Proposed feature

- A `firebird.quickQueries` setting: an array of `{ name, sql, action: "run" | "open" }` entries (mssql's own execute-immediately vs open-for-review choice, per entry rather than global).
- A fixed set of `firebird.quickQuery.1` … `firebird.quickQuery.9` commands contributed with titles derived from nothing (the entry's `name` can't reach the keybinding UI) but with `category: "Firebird"` so they're findable in the Keyboard Shortcuts editor. Each looks up its index in `firebird.quickQueries` and either runs the SQL or opens it in an untitled `.sql` editor. Shipping *no* default keybindings is the right call — every plausible combo is already taken, and the whole point is that users pick their own.
- **Execution must go through `runSqlBatch()`** (`src/extension.ts`, the shared runner behind `firebird.runQuery`/`firebird.runCurrentStatement`), not a fresh `Driver.runQuery()` call — that's what gets a Quick Query the same multi-statement splitting, DDL-success notification plus Object Explorer refresh, query-history logging, and `{notify, message, options}` error handling every other run path already has.
- **Selected-text support** (mssql 1.44.1): a `${selectedText}` placeholder in the stored SQL, substituted from the active editor's selection before running — this is what makes a single binding useful, e.g. `SELECT COUNT(*) FROM ${selectedText}` over a highlighted table name. Needs an explicit decision on the empty-selection case: substituting an empty string silently produces broken SQL, so it should refuse with a clear message instead.
- **Reuse the bookmark store rather than adding a second saved-query store.** A `slot?: number` field on the existing bookmark model plus an "Assign to Quick Query Slot" tree action gives management UI, persistence, and rename/delete for free, and avoids the state-drift problem of the same query existing in two places. The `firebird.quickQueries` *setting* is still worth having alongside it for settings-sync/workspace-shared queries — but only one of the two should be the source of truth per slot, with the setting winning if both define one.
- **Skip mssql's Shortcuts Configuration webview.** Once the numbered commands exist, VS Code's built-in Keyboard Shortcuts editor already does the binding half, and the bookmarks tree already does the management half. A custom webview duplicating both is the least valuable part of this feature.
