# Language Model Tools (Copilot agent mode without MCP)

**Inspired by**: VS Code 1.95's finalized extension API — "We have finalized our [`LanguageModelTool` API](https://code.visualstudio.com/api/references/vscode-api#lm.tools)! This API enables chat extensions to build more powerful experiences by connecting language models to external data sources, or take actions." Both [vscode-mssql](https://github.com/microsoft/vscode-mssql) (1.43.0) and [vscode-pgsql](https://github.com/microsoft/vscode-pgsql) (1.27.0) have since moved their Copilot integrations to GA, and agent-mode tool calling — not a mention-based chat participant — is the shape that integration has settled into.

## Current state in Firebird Studio

**All four phases are done.**

- **Phase 1 — one implementation, two transports — done.** New `src/shared/db-tools.ts` holds all five tool bodies (`listConnectionsTool`, `getSchemaTool`, `runQueryTool`, `getQueryPlanTool`, `runWriteQueryTool`) plus the shared `TOOL_DESCRIPTIONS`, behind a `ToolExecutor` seam with three members: `listConnections()`, `withConnection(id, run)`, and an optional `audit(entry)`. Everything that differs between transports (how you get a connection, how you run a statement, where an audit entry goes) is behind that interface; everything that must *not* differ (what's refused, what the write gate checks, how results are shaped, what the model is told) lives in the shared module. `src/mcp-server/server.ts` dropped from 293 to 222 lines and now only supplies its own executor (raw `node-firebird`, one attach per tool call, audit lines appended to the file the host tails). The module imports nothing from `vscode` and can't — the MCP subprocess is a plain Node process — so it only uses `queries.ts`/`schema-graph.ts`/`sql-analysis.ts`, which that subprocess already depended on.
  - `withConnection(id, run)` rather than a flat `query(id, sql)` specifically so `get_schema`'s two metadata statements still share one connection instead of reconnecting per statement, exactly as the original inline code did. Verified by a test asserting `connectCount === 1` for that tool.
- **Phase 2 — read-only tools — done.** `src/copilot/lm-tools.ts` registers all five via `vscode.lm.registerTool`, with matching `contributes.languageModelTools` entries (each with a `toolReferenceName` — `#firebirdConnections`, `#firebirdSchema`, `#firebirdQuery`, `#firebirdQueryPlan`, `#firebirdWriteQuery` — so they work as explicit references in ask mode as well as automatic agent-mode tools). `modelDescription` text carries the Firebird dialect notes the model actually needs (`FIRST n SKIP m`/`OFFSET`-`FETCH` rather than `LIMIT`, uppercase identifier folding, `RDB$` system tables). Registration is guarded on `vscode.lm.registerTool` existing, mirroring how the chat participant guards `vscode.chat`, so the vscode-host activation test never depends on which APIs the running build has.
  - **Connection scope deliberately differs from the MCP server's.** The MCP server only ever sees connections explicitly marked `mcpExposed`, because it serves clients *outside* VS Code. These tools run in the extension host on behalf of the user's own Copilot session, at the same trust boundary the `@firebird` chat participant already operates at (it reads the active connection's schema with no separate opt-in), so they see every saved connection — the same set `connection-sharing`'s `listConnections()` returns.
  - The host executor connects via `Driver.client.createConnection()`/`queryPromise()`/`detach()` rather than `Driver.runQuery()`. That's not incidental: `runQuery()` substitutes its own `[{message: "..."}]` array for a statement with no result set, which would have made `run_write_query` report differently depending on which transport ran it. Going through the client directly preserves the raw `undefined` the shared code is written against. `Driver.resolvePassword()` is called first, as that method's own doc comment requires of anyone bypassing `runQuery()`/`runBatch()`.
- **Phase 3 — write tool — done.** `run_write_query` keeps the *existing* `mcpWriteEnabled` per-connection opt-in (no second gate invented) and adds `prepareInvocation()` returning `confirmationMessages` with the exact statement rendered as SQL — agent mode invokes tools unattended, and that callback is the API's own affordance for "this mutates something, ask first". The connection gate still applies on top: a connection without write access refuses even after the user confirms. Every attempt, including both refusal paths, goes through `audit()`, which in the host logs to the existing output channel rather than the subprocess's audit file.
- **Phase 4 — version alignment — done, and it turned up a real problem.** Pinning `@types/vscode` immediately failed the build: `src/mcp-server/index.ts` references `vscode.McpServerDefinitionProvider` and `vscode.McpStdioServerDefinition`, which are **1.101** APIs, while `engines.vscode` claimed `^1.93.0`. The runtime was always correctly guarded (MCP simply doesn't register on older builds), so the extension really did *run* on 1.93 — but nothing could have caught an unguarded newer-API use, because `@types/vscode: ^1.32.0` resolved to 1.125.0. Resolved by raising `engines.vscode` to `^1.101.0` and pinning `@types/vscode` to `~1.101.0` (`~`, not `^` — `^1.101.0` would resolve to the latest 1.x and reintroduce the exact drift). This drops VS Code 1.93–1.100 users, which was an explicit call rather than a silent one.

### Testing

`src/test/db-tools.test.ts` (18 tests) covers all five tools against a fake `ToolExecutor` — no database, no MCP client, no extension host — which none of this logic had before, since it was previously inline in a subprocess only reachable over stdio. Covered: `list_connections` output shape including `writeEnabled`; all four id-taking tools refusing an unknown id with the same `list_connections` guidance *and* never opening a connection; `get_schema` running both statements on one connection; read-only enforcement across DELETE/UPDATE/INSERT/DROP/EXECUTE BLOCK, each refused before connecting; the no-result-set and query-failure paths; `get_query_plan` skipping the database entirely when no table is recognized and passing table names as parameters when one is; and the full write path — the not-write-enabled refusal, the non-write-statement refusal, a successful write, a `RETURNING` result, a failed write, each with its expected audit entry, plus an executor with no `audit()` at all (auditing is best-effort and must never break a write).

`src/test/suite/lm-tools-integration.test.ts` (4 tests) covers what only a real host can: that every `contributes.languageModelTools` entry is actually registered under the same name (a mismatch there is silent and would leave a contributed tool permanently unimplemented), that each carries a model-facing description, and two real `vscode.lm.invokeTool()` round trips — `firebird_listConnections` returning parseable JSON, and `firebird_runWriteQuery` refusing an unresolvable connection id before reaching any database, confirmation prompt, or write.

The refactored MCP subprocess was additionally verified **live over real stdio JSON-RPC** against the Firebird 6 server: `tools/list` returns all five, `run_query` returns real rows from the seeded `PRODUCTS` table, `run_query` refuses a `DELETE`, `run_write_query` is blocked by the write gate, `get_schema` returns a real schema graph, and an unknown connection id is reported correctly. Full pass: `tsc` clean on all three configs, `npm run test` → 1369 passing (18 new), `npm run compile` clean (including the separate MCP bundle, re-checked for any `require("vscode")` — none), `npx eslint` clean on every touched file, `npm run test:vscode-host` → **104 passing, 0 failing**.

### Original state (before this item)

The extension already had three separate AI surfaces, and this was the one that was missing:

- **`@firebird` chat participant** (`src/copilot/`, `/query`, `/optimize`, `/explain`) — only reachable when the user explicitly types `@firebird`. Registered conditionally on `typeof vscode.chat !== 'undefined'`.
- **Direct model calls** via `vscode.lm.selectChatModels({ vendor: "copilot" })` in `src/schema-designer/index.ts`, `src/flat-file-import/index.ts`, `src/data-api-builder/index.ts`, and `src/copilot/ai-query-actions.ts` — the extension drives the model, not the reverse.
- **MCP server** (`src/mcp-server/`) exposing `list_connections`, `get_schema`, `run_query`, `get_query_plan` (read-only) and the opt-in `run_write_query`, registered through `vscode.lm.registerMcpServerDefinitionProvider` and gated behind the `firebird.mcpEnabled` setting. Note that `server.registerTool` in `src/mcp-server/server.ts` is the **MCP SDK's** method, not VS Code's.
- **`vscode.lm.registerTool` and `contributes.languageModelTools` are used nowhere** — confirmed by grep: no `languageModelTools` key in `package.json`'s `contributes` (which has `chatParticipants` and `mcpServerDefinitionProviders` but not this), and no `LanguageModelTool` anywhere under `src/`.

The practical consequence: in Copilot **agent mode**, Firebird is reachable only if the user has found and enabled `firebird.mcpEnabled` and has an MCP-capable client running. A `languageModelTools` contribution is offered to any agent request automatically, and to normal chat via a `#`-reference, with no MCP hop and no separate server process.

### Version constraint (needs deciding before phase 4)

`package.json` declares `engines.vscode: ^1.93.0`, so adopting this API requires raising the floor to `^1.95.0`. Worth fixing at the same time: `devDependencies["@types/vscode"]` is `^1.32.0`, which npm resolves to **1.125.0** — the compiler currently accepts APIs from 30+ releases beyond the declared engine floor, so nothing would have caught an accidental post-1.93 API use today either. The two should be pinned to the same minor.

## Proposed feature

- **One implementation, two transports.** The five MCP tool bodies in `src/mcp-server/server.ts` are already the exact operations a language model wants; the work is extracting them into a transport-agnostic module (taking a connection + arguments, returning structured data) that both the MCP server and a set of `LanguageModelTool` implementations call. Re-implementing them against `vscode.lm` while leaving the MCP copies in place would give two behaviors, two error shapes, and — critically — two write paths to keep in sync with one audit log.
- **`contributes.languageModelTools` entries** with `toolReferenceName`s (`#firebirdSchema`, `#firebirdQuery`, …) so they work as explicit `#`-references in ask mode as well as automatic agent-mode tools, plus `modelDescription` text that tells the model Firebird's dialect specifics (`FIRST`/`ROWS` instead of `LIMIT`, `RDB$` system tables) — the same context `src/copilot/schema-context.ts` already assembles for the chat participant.
- **Reuse the existing write gate for the write tool.** `run_write_query`'s opt-in setting and audit log already exist; the LM-tool version should sit behind the same gate rather than a parallel one, and additionally implement `prepareInvocation()` to return a confirmation message — that callback is exactly the API's affordance for "this tool mutates something, ask first", and agent mode will otherwise call it unattended.
- **Don't retire the MCP server.** It serves clients outside VS Code; this is an additional transport for the in-editor case, not a replacement.
